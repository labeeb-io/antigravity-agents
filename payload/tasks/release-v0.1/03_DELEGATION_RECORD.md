## بيان التفويض الرسمي

أقر صاحب المنتج اعتماد Shipping Mode وميثاق v0.1، ويفوض **Release Coordinator** بقيادة العمل اليومي تلقائياً داخل الميثاق المجمد دون تحويل المؤسس إلى ناقل رسائل بين الوكلاء.

## 1. صلاحيات Release Coordinator المفوضة

يجوز له دون موافقة يومية جديدة:
1. تحديد أول proof target غير محسوم من الميثاق والأدلة الحالية.
2. إدارة `WIP = 1` وتحديث [00_RELEASE_CONTROL.md](./00_RELEASE_CONTROL.md) والسبرينت والتقارير التشغيلية.
3. استدعاء `discovery-coordinator` ووكلاء البحث المقيدين لجمع الأدلة.
4. تفويض تجربة محلية واحدة محددة وقابلة للعكس عند الحاجة لإثبات Finding، بشرط عدم تعديل الكود أو المخطط أو النشر أو البنية التحتية.
5. تحويل Finding روتيني مثبت داخل الميثاق إلى Task Contract واحد تلقائياً إذا استوفى بوابة القبول ولم يلمس قراراً محفوظاً للمؤسس.
6. استدعاء `implementation-executor` ومتابعته وإرسال targeted correction داخل نفس العقد عند الحاجة.
7. استدعاء `release-auditor` مستقلاً وإعادة مسار الإثبات الأصلي.
8. اعتماد إغلاق المهمة البرمجية الروتينية بعد `PASS` مستقل بالدليل.
9. رفض/تأجيل أي توسيع خارج v0.1 حتى لو ظهر أثناء النقاش اليومي.
10. استخدام Native Antigravity subagents أولاً، واستخدام Orchestrator داخلياً كـfallback أو عند الحاجة إلى نموذج خارجي، دون مطالبة المؤسس بنقل الحزم بين الجلسات.

## 2. حدود التنفيذ البرمجي والبيئات

- **Implementation Executor:** تعديل محلي داخل `allowed_scope` فقط؛ لا push ولا merge ولا deploy ولا تعديل governance.
- **Release Coordinator:** يملك إجراءات النشر/الدمج الروتينية التي سبق أن فوضها هذا السجل فقط بعد نجاح التحقق المطلوب والسياسات التشغيلية؛ الأداة نفسها قد تطلب موافقة تشغيلية للأمر الخطر ولا يعد ذلك تغييراً في التفويض.
- **Production state-changing probes:** تجربة جديدة تنشئ بيانات/جلسات في الإنتاج خارج مسار تنفيذ روتيني مجاز تحتاج عقداً محدداً وموافقة صريحة قبل أول محاولة.
- **Independent Auditor:** قراءة وفحص فقط، ويكتب تقريره في `reports/`؛ لا يصلح الكود.

## 3. القرارات المحفوظة حصراً للمؤسس

1. تعديل ميثاق الإصدار أو وعد المنتج أو فتح نطاق جديد.
2. ميزانية/اشتراكات/تكاليف غير اعتيادية.
3. مخاطر أمنية أو قانونية أو سرية بيانات جوهرية.
4. تغيير معماري كبير أو استبدال منظومة رئيسية.
5. الاعتماد الأسبوعي النهائي لمعايير الإصدار.
6. قرار إطلاق النسخة للجمهور (`Go / No-Go`).

أي Finding أو إصلاح لا يدخل في البنود أعلاه **لا يحتاج Owner Gate جديداً** إذا كان داخل الميثاق والتفويض وWIP=1.

## 4. الاستقلال والشفافية

- من يكتب التعديل لا يمنح نفسه PASS النهائي.
- يمكن للمؤسس مراقبة التسلسل من Agent Manager/التقارير، لكن لا يلزم أن يعيد تمرير رسائل الوكلاء.
- عند تعذر native subagents، يجب توثيق Orchestrator task/session ID حتى تبقى المصالحة قابلة للتتبع.

## 5. المراجعة الأسبوعية

يعرض Release Coordinator الأدلة المكتملة للمعايير. عدم رد المؤسس يبقي اعتماد المعيار `قيد المراجعة` لكنه لا يوقف الأعمال الفنية الروتينية المفوضة التي لا تعتمد على القرار.
